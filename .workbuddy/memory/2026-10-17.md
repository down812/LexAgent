## 修复·Python 3.13 安装 paddlepaddle 报错

### 问题
用户系统 Python 是 3.13.5，运行 `pip install paddlepaddle==2.6.1` 报错：
`ERROR: No matching distribution found for paddlepaddle==2.6.1`

### 根因
PaddlePaddle 2.6.x **不支持 Python 3.13**（2.6.x 仅支持 3.8-3.12）。
且 PyPI 上的 paddlepaddle 只有 2.6.x，3.x 版本只在百度官方源发布。

### 解决方案：升级到 PaddlePaddle 3.x + PaddleOCR 3.x
- PaddlePaddle 3.0.0+ 支持 Python 3.9-3.13（包括 3.13）✅
- PaddleOCR 3.x 需要 PaddlePaddle ≥ 3.0.0
- **paddlepaddle 必须用百度官方源**：`-i https://www.paddlepaddle.org.cn/packages/stable/cpu/`
- PaddleOCR 3.x 与 2.x **API 不兼容**，需迁移代码

### PaddleOCR 2.x → 3.x API 迁移对照
| 2.x | 3.x |
|---|---|
| `ocr.ocr(img, cls=True)` | `ocr.predict(img)` |
| `use_angle_cls=True` | `use_textline_orientation=True` |
| `use_gpu=True` | `device="gpu"` |
| `show_log=False` | 移除（用 logging） |
| `[[box, (text, score)], ...]` | `res["rec_texts"]` / `res["rec_scores"]` / `res["rec_boxes"]` |

### 文件改动
- requirements.txt：移除 paddlepaddle（改在 install 脚本里用官方源装），paddleocr 改为 `>=3.0.0,<4.0.0`
- ocr_engine.py：**全面适配 3.x API**
  - `PaddleOCR(use_angle_cls=True, lang="ch", show_log=False)` → `PaddleOCR(lang="ch", device="cpu", use_textline_orientation=True, use_doc_orientation_classify=False, use_doc_unwarping=False)`
  - `ocr.ocr(img, cls=True)` → `ocr.predict(img)`
  - 结果解析：从嵌套列表 `[[box, (text, score)], ...]` 改为字典式 `res["rec_texts"]` / `res["rec_scores"]` / `res["rec_boxes"]`
  - box 从 4 点多边形改为 `[x1, y1, x2, y2]` 水平外接框，y 排序用 `box[1]`
- 新增 install.bat / install.sh：两步安装（先 paddlepaddle 3.x 官方源，再 requirements.txt）
- README.md：更新安装说明、加迁移对照表、加常见问题
- Java 端 OcrClient **无需改动**（HTTP 接口契约 /ocr/recognize、/ocr/recognize_pdf 返回 {text, pages, length} 未变）

## 修复·.bat 脚本中文乱码导致命令执行失败

### 问题
用户运行 install.bat 报错（'dlepaddle' 不是内部或外部命令 等一堆乱码错误）。

### 根因
Write 工具写出的 .bat 文件是 UTF-8 编码，但 Windows cmd 默认用 GBK(CP936) 解码批处理文件。
`chcp 65001` 在执行时才切代码页，但此时文件已被错误解析，中文 echo 字节被 GBK 错误解码，
连累后续命令被截断/拼接，导致一串乱码命令错误。

### 解决
把 install.bat 和 start.bat **全部改成纯 ASCII 英文**（注释和 echo 输出都用英文）。
用 ripgrep 验证无非 ASCII 字节（`[^\x00-\x7F]` 无匹配）。
.sh 脚本（Linux/Mac）保留中文，shell 对 UTF-8 支持良好无此问题。

### 教训（长期记住）
**Windows .bat / .ps1 脚本必须纯 ASCII**，任何中文（注释、echo、路径）都会在 GBK 系统上乱码。
要中文输出就用 Python 脚本或 .ps1 配合 UTF-8 BOM，.bat 永远只用英文。

## 修复·PaddleOCR 3.7 报 strides 错误（PaddlePaddle 版本不匹配）

### 问题
用户在 /docs 测试 OCR 时报错：
`ValueError: Type of attribute: strides is not right`
发生在 `paddle_inference.create_predictor(config)` 阶段（模型加载时）。

### 根因
PaddleOCR 3.7.0 对模型结构优化，把 strides 等参数从 Int64 改成 Int32 类型，
而 PaddlePaddle 3.0.0 的推理引擎还是旧格式无法解析 → 类型校验失败。
即 **PaddleOCR 3.7.0 与 PaddlePaddle 3.0.0 版本不匹配**。

### 解决
升级 PaddlePaddle 3.0.0 → **3.2.1**（paddleocr.dev 官方推荐与 PaddleOCR 3.7.0 匹配的版本）：
```
pip install --upgrade paddlepaddle==3.2.1 -i https://www.paddlepaddle.org.cn/packages/stable/cpu/
```
然后重启 OCR 服务（无需重装 paddleocr）。

### 文件改动
- install.bat：paddlepaddle==3.0.0 → 3.2.1（注释和命令都改）
- README.md：所有 paddlepaddle==3.0.0 → 3.2.1（CPU 版）、paddlepaddle-gpu==3.0.0 → 3.2.1（GPU 版）

## 修复·PaddleOCR 3.7 结果解析报 ambiguous 真值错误

### 问题
用户在 /docs 测试 OCR 时报错：
`ValueError: The truth value of an array with more than one element is ambiguous. Use a.any() or a.all()`
发生在 `ocr_engine.py:56 boxes = res.get("rec_boxes") or []` 行。

### 根因
PaddleOCR 3.x 的 `res.get("rec_boxes")` 返回的是 **numpy array**（不是 Python list）。
`or []` 短路求值会对左侧对象做真值判断（`bool(array)`），而 numpy array 元素数 >1 时
真值判断是 ambiguous 的，触发该错误。`rec_texts` / `rec_scores` 同理。

### 解决
把 `or []` 短路求值改为**显式 None 判断 + list() 转换**：
```python
# 旧（错误）
texts = res.get("rec_texts") or []
boxes = res.get("rec_boxes") or []

# 新（正确）
texts = res.get("rec_texts")
scores = res.get("rec_scores")
boxes = res.get("rec_boxes")
if texts is None or scores is None or boxes is None:
    continue
texts = list(texts); scores = list(scores); boxes = list(boxes)
```
显式 None 判断避开 numpy array 真值问题；list() 转换统一后续迭代行为。

### 教训（长期记住）
**处理 numpy array 返回值时，永远不能用 `x or default` 短路求值**——要显式 `if x is None`。
PaddleOCR / PaddlePaddle / scikit-learn 等库返回值常为 numpy array，都需注意。

## 修复·OCR 调用超时（PDF 多页 5 分钟 read timeout）

### 问题
用户上传扫描 PDF，Java 端报 `Read timed out`：
上传 23:36:49 → 失败 23:41:49，正好 5 分钟（300秒）= 当时 read-timeout-ms: 300000。

### 根因
旧架构：Java 端把整个 PDF 文件传给 Python `/ocr/recognize_pdf`，
Python 端用 PyMuPDF 拆页 → 逐页 OCR → 合并文本 → 一次性返回。
**单次 HTTP 请求耗时 = 所有页 OCR 时间总和**，页数多就超时，且无法输出进度。

### 解决：架构改造（治本）
把 PDF 拆页从 Python 端移到 **Java 端用 PDFBox** 做：
- Java 端 `OcrClient.recognizePdf` 用 PDFBox `PDFRenderer.renderImageWithDPI` 渲染每页为 PNG
- 逐页调 `/ocr/recognize`（单图 OCR，每次 3-5 秒）→ 累加文本
- 临时图片放系统 temp 目录，用完即删

好处：
1. 每次 HTTP 请求只 OCR 一页（3-5秒），**永不超时**
2. 实时进度日志（"第 3/10 页 OCR 完成，耗时=4200ms"）
3. 单页失败可跳过，不影响其他页（只记录 warn）
4. 不传整个 PDF 给 Python，减少网络传输
5. Python 端 `/ocr/recognize_pdf` 保留但 Java 不再依赖

### 配置改动
- `read-timeout-ms`: 300000 → **60000**（单页 OCR 3-5 秒，60 秒兜底足够）
- 注释更新说明新架构

### 文件改动
- `OcrClient.java`：重写 `recognizePdf`，新增 `doRecognizeImage` 私有方法
- `application-rag.yaml`：read-timeout-ms 默认值 300000 → 60000，注释说明新架构
