LexAgent 智能法律援助系统
=================

V2.0 功能需求规格说明书
==============

**项目名称：** 基于 Multi-Agent 与 RAG 的智能法律援助系统（LexAgent）  
**文档版本：** V2.0  
**文档类型：** 软件需求规格说明书（SRS）  
**前置版本：** V1.0  
**开发基础：** 已完成的 V1.0 项目源代码  
**核心升级方向：** 案件管理、证据智能处理、法律辅助决策、回答质量评估

第一章 项目概述
========

1.1 项目背景
--------

LexAgent 是一套基于多智能体协作（Multi-Agent）与检索增强生成（RAG）技术的智能法律援助系统。

V1.0 已经完成系统基础功能建设，实现了用户管理、法律知识库管理、OCR 文档识别、法律法规检索、多 Agent 协作分析、法律依据核验以及 SSE 流式问答等功能。

但是，当前系统主要解决的是用户提出法律问题后，系统如何检索法律法规并生成法律分析的问题。

在实际法律援助场景中，用户往往不仅需要了解法律法规，还需要：

1. 对自己的案件进行长期管理。

2. 整理和保存与案件相关的证据材料。

3. 从合同、聊天记录、转账截图等材料中提取关键信息。

4. 根据案件情况判断还缺少哪些证据。

5. 了解案件涉及的法律风险和争议焦点。

6. 对系统生成的法律建议进行评价和反馈。

因此，V2.0 将系统从单纯的智能法律问答工具升级为具备案件管理、证据辅助分析和法律知识服务能力的智能法律援助平台。
1.2 V2.0 建设目标
-------------

V2.0 主要实现以下目标：

* 建立独立的案件管理体系，实现案件创建、编辑、查询、归档。

* 建立案件证据管理体系，实现证据上传、分类、OCR 识别和关联。

* 引入证据分析能力，提取证据中的关键内容。

* 实现智能证据清单生成，根据案件事实和争议焦点提示证据需求。

* 优化多 Agent 协作流程，使案件分析与证据分析能够协同工作。

* 建立法律问答反馈与质量评估体系。

* 优化法律知识库的管理和维护能力。

* 提升系统的可追溯性、稳定性和实用性。

1.3 版本定位
--------

V1.0：

以法律智能问答为核心，实现法律法规检索、案件初步分析和法律依据核验。

V2.0：

以案件为核心，实现案件信息管理、证据材料管理、智能证据分析和法律辅助决策。

整体升级：
    V1.0用户提出法律问题        |        v多 Agent 协作        |        vRAG 法律法规检索        |        v法律分析与审核        |        v法律问答结果V2.0用户创建案件        |        v案件信息管理        |        v证据材料上传与管理        |        vOCR 识别与证据内容提取        |        v案件事实与证据关联        |        v多 Agent 协作分析        |        vRAG 法律法规检索        |        v法律分析与风险审核        |        v证据清单与处理建议        |        v案件持续管理

第三章 案件管理模块
==========

3.1 模块目标
--------

V1.0 中已经具备会话管理功能，但会话主要用于保存用户与 AI 的问答记录。

V2.0 引入独立的案件管理概念。

一个案件可以包含：

* 案件基本信息。

* 案件事实。

* 争议焦点。

* 多次法律问诊记录。

* 证据材料。

* 证据分析结果。

* 法律法规依据。

* 处理建议。

* 案件处理状态。

需要区分：

**会话（Conversation）：** 用户与 AI 的一次或多次问答记录。

**案件（Case）：** 用户需要持续管理的实际法律事务。

一个案件可以关联多个问诊会话，一个会话原则上关联一个案件。
3.2 案件创建
--------

功能编号：CASE-001

用户可以创建新的法律案件。

输入信息：

| 字段   | 说明         | 是否必填 |
| ---- | ---------- | ---- |
| 案件名称 | 用户自定义案件名称  | 是    |
| 案件类型 | 劳动纠纷、合同纠纷等 | 是    |
| 案件描述 | 案件基本情况     | 是    |
| 发生时间 | 案件发生时间     | 否    |
| 发生地点 | 案件发生地点     | 否    |
| 涉及主体 | 公司、个人等     | 否    |
| 备注   | 补充信息       | 否    |

案件类型建议：

* 劳动争议。

* 合同纠纷。

* 消费者权益纠纷。

* 借贷纠纷。

* 房屋租赁纠纷。

* 婚姻家庭纠纷。

* 人身损害纠纷。

* 其他民事纠纷。

处理流程：
    用户进入案件管理页面        |        v点击创建案件        |        v填写案件基本信息        |        v后端参数校验        |        v保存案件信息        |        v生成案件编号        |        v进入案件详情页面
3.3 案件列表
--------

功能编号：CASE-002

系统提供案件列表页面。

展示字段：

* 案件编号。

* 案件名称。

* 案件类型。

* 案件状态。

* 创建时间。

* 最近更新时间。

支持：

* 按案件名称查询。

* 按案件类型筛选。

* 按案件状态筛选。

* 按创建时间排序。

* 分页查询。

案件状态：

| 状态        | 说明    |
| --------- | ----- |
| ACTIVE    | 进行中   |
| PENDING   | 待补充信息 |
| COMPLETED | 已完成   |
| ARCHIVED  | 已归档   |

3.4 案件详情
--------

功能编号：CASE-003

用户点击案件列表中的案件，可以进入案件详情页面。

页面划分：

1. 案件基本信息。

2. 案件事实。

3. 争议焦点。

4. 关联问诊记录。

5. 证据材料。

6. 法律分析记录。

7. 处理建议。

3.5 案件编辑
--------

功能编号：CASE-004

用户可以修改案件基本信息。

支持：

* 修改案件名称。

* 修改案件类型。

* 修改案件描述。

* 修改案件发生时间。

3.6 案件归档
--------

功能编号：CASE-005

用户可以将已经结束的案件进行归档。

归档要求：

* 归档后案件不再显示在默认进行中列表。

* 用户仍然可以查看案件详情。

* 历史问诊记录和证据材料保留。

* 不允许普通用户查看其他用户的案件。

3.7 案件与问诊会话关联
-------------

功能编号：CASE-006

用户可以在案件详情中发起法律问诊。

系统将新创建的问诊会话与当前案件关联。

关联关系：
    Case | +---- Conversation 1 | +---- Conversation 2 | +---- Conversation 3        |        +---- Messages

要求：

* 案件可以关联多个会话。

* 用户可以查看案件下的全部问诊历史。

* 会话仍然保留原有历史消息管理能力。

* 删除或归档会话不得直接删除案件。

* 归档案件不得导致关联证据丢失。

第五章 智能证据分析模块
============

5.1 模块目标
--------

在 OCR 的基础上增加法律场景下的证据内容理解能力。

OCR 负责识别文字，证据分析负责理解文字。

例如，用户上传一份劳动合同。

系统不仅要识别合同中的文字，还应尝试提取：

* 合同签订主体。

* 合同签订日期。

* 合同期限。

* 岗位信息。

* 工资约定。

* 试用期。

* 解除劳动合同相关约定。

注意：系统提取的是文档中出现的信息，不得将模型推测内容当成合同原文。
5.2 证据关键信息提取
------------

功能编号：EVIDENCE-006

系统调用大语言模型分析 OCR 结果。

输入：
    {  "caseType": "劳动争议",  "fileName": "劳动合同.pdf",  "ocrText": "合同正文识别内容..."}

输出示例：
    {  "evidenceType": "劳动合同",  "parties": [    "某某公司",    "张某"  ],  "keyInformation": [    {      "field": "合同期限",      "value": "2025年1月1日至2026年12月31日",      "sourceText": "原文对应内容"    },    {      "field": "工资标准",      "value": "每月8000元",      "sourceText": "原文对应内容"    }  ],  "uncertainInformation": []}

要求：

* 输出结构化 JSON。

* 每项提取结果尽可能关联原文。

* 无法识别的信息明确标记。

* 不允许补充原文不存在的信息。

* 支持用户人工修正。

5.3 证据分类推荐
----------

功能编号：EVIDENCE-007

根据 OCR 结果和案件类型推荐证据分类。

例如：

输入：
    银行转账记录转账金额：50000元转账日期：2026年3月12日

推荐：
    {  "category": "财务凭证",  "evidenceType": "银行转账记录",  "confidence": 0.92}

要求：

* 系统提供分类建议。

* 用户可以接受或修改建议。

* 低置信度时不自动确认分类。

5.4 证据与案件事实关联
-------------

功能编号：EVIDENCE-008

系统将证据内容与案件事实进行关联。

例如：

案件事实：
    用户称公司拖欠三个月工资。

上传证据：
    银行工资流水。

系统可以提示：
    该证据可能与以下案件事实相关：1. 工资支付情况2. 拖欠工资时间3. 实际到账金额

要求：

* 关联结果必须给出依据。

* 不允许直接认定证据真实性。

* 用户可以确认或取消关联。

* 关联结果可以在案件详情中查看。

5.5 证据完整性分析
-----------

功能编号：EVIDENCE-009

根据案件类型、案件事实和争议焦点，对已有证据进行辅助分析。

输出：

* 已有证据。

* 证据覆盖的案件事实。

* 尚未覆盖的案件事实。

* 建议补充的材料。

* 需要进一步核实的信息。

系统只能提供辅助整理建议，不得宣称证据必然被法院采纳。

第六章 智能证据清单生成模块
==============

6.1 模块目标
--------

根据案件事实和法律争议焦点，为用户生成个性化证据清单。

这是 V2.0 的重点功能之一。
6.2 证据清单生成
----------

功能编号：LIST-001

用户可以在案件详情页面点击：

**生成证据清单**

系统将以下信息作为输入：

* 案件类型。

* 案件基本事实。

* 争议焦点。

* 已上传证据。

* 已提取的证据内容。

* 相关法律知识库检索结果。

生成证据清单。

示例：

用户案件：
    公司拖欠工资三个月，用户准备申请劳动仲裁。

系统生成：

| 证据名称     | 用途       | 当前状态 |
| -------- | -------- | ---- |
| 劳动合同     | 证明劳动关系   | 待上传  |
| 工资流水     | 证明工资支付情况 | 已上传  |

第七章 Multi-Agent 协作升级
====================

7.1 当前 Agent 架构
---------------

V1.0 已经实现：

1. Case Analysis Agent。

2. Legal Search Agent。

3. Legal Analysis Agent。

4. Reviewer Agent。

5. Supervisor Agent。

现有流程：
    用户问题   |   vSupervisor Agent   |   vCase Analysis Agent   |   vLegal Search Agent   |   vRAG 混合检索   |   vLegal Analysis Agent   |   vReviewer Agent   |   v最终法律回答
7.2 V2.0 Agent 架构
-----------------

增加 Evidence Analysis Agent。

新架构：
                     用户                  |                  v            Supervisor Agent                  |          +-------+-------+          |               |          v               v   Case Analysis      Evidence Analysis       Agent              Agent          |               |          +-------+-------+                  |                  v          Legal Search Agent                  |                  v             RAG 检索                  |                  v          Legal Analysis Agent                  |                  v             Reviewer Agent                  |                  v             最终回答

具体执行顺序应根据用户请求类型进行判断，不要求所有 Agent 每次都执行。
7.3 Evidence Analysis Agent
---------------------------

功能编号：AGENT-001

负责分析案件证据材料。

输入：

* 案件信息。

* 案件事实。

* OCR 识别结果。

* 已上传证据。

* 证据清单。

输出：

* 证据类型。

* 关键信息。

* 证据关联事实。

* 证据缺失情况。

* 证据分析建议。

7.4 Supervisor Agent 升级
-----------------------

功能编号：AGENT-002

Supervisor Agent 根据用户请求决定是否调用 Evidence Analysis Agent。

场景一：普通法律咨询。
    用户问题  |  vCase Analysis  |  vLegal Search  |  vLegal Analysis  |  vReviewer

场景二：案件证据分析。
    用户请求  |  vCase Analysis  |  vEvidence Analysis  |  vLegal Search  |  vLegal Analysis  |  vReviewer

要求：

* Agent 输入输出保持结构化。

* 记录每个 Agent 的执行状态。

* 记录执行耗时。

* 记录异常信息。

* 支持失败降级。

* 保持 V1.0 已有 SSE 事件推送能力。

7.5 Reviewer Agent 升级
---------------------

功能编号：AGENT-003

在现有法律依据核验基础上增加证据分析结果检查。

检查：

1. 是否引用不存在的证据。

2. 是否将用户未提供的材料当成已有证据。

3. 是否错误提取证据内容。

4. 是否将模型推测当成确定事实。

5. 是否存在绝对化法律结论。

6. 是否对证据不足的情况作出说明。

第八章 法律智能问诊升级
============

8.1 案件上下文问答
-----------

功能编号：CHAT-001

V2.0 支持在案件详情中进行上下文问答。

系统自动获取：

* 案件基本信息。

* 案件事实。

* 已有证据。

* 证据分析结果。

* 历史问诊记录。

用户无需每次重复描述案件情况。
8.2 案件信息补充
----------

功能编号：CHAT-002

当系统发现案件关键信息缺失时，可以向用户追问。

例如：
    目前还需要确认：1. 公司是否向你出具解除劳动合同通知？2. 你最近三个月的平均工资是多少？3. 是否保留考勤记录？请根据实际情况补充。

要求：

* 追问必须与当前案件相关。

* 用户可以选择暂时跳过。

* 用户补充后更新案件事实。

* 不允许系统擅自补全未知事实。

8.3 案件上下文隔离
-----------

功能编号：CHAT-003

不同案件之间的上下文必须隔离。

要求：

* 案件 A 的证据不能用于案件 B。

* 案件 A 的历史消息不能默认作为案件 B 的事实。

* 每次问诊必须明确所属案件。

* 未关联案件的普通问答仍然支持 V1.0 原有流程。

第十五章 非功能需求
==========

15.1 安全性
--------

* 所有需要登录的接口必须进行 JWT 身份认证。

* 用户只能访问自己所属的案件。

* 用户不能通过修改案件 ID 访问其他用户的证据。

* 文件上传需要校验扩展名和实际文件类型。

* 对文件大小进行限制。

* 敏感信息不得在普通日志中完整输出。

* OCR 文件应进行安全存储。

* 删除案件或证据时应遵循关联数据处理规则。

15.2 可靠性
--------

* OCR 失败不得导致案件信息丢失。

* Agent 执行失败需要记录异常。

* 证据分析失败允许重新执行。

* 文件处理任务应避免重复执行。

* SSE 断开不得破坏已经保存的历史记录。

15.3 性能要求
---------

* 案件列表采用分页查询。

* 证据列表采用分页查询。

* 文件上传与 OCR 处理尽量异步化。

* 大文件处理应避免阻塞普通 HTTP 请求。

* Agent 执行过程继续采用异步执行和 SSE 推送。

* 对重复分析任务进行必要的控制。

15.4 可维护性
---------

* 新增业务采用 Controller、Service、Mapper、Entity 分层。

* Agent 使用独立 Service 实现。

* Prompt 统一管理。

* 新增接口统一使用 Result 返回结构。

* 数据库变更采用增量 SQL 脚本。

* 记录关键业务操作和异常日志。

15.5 法律安全要求
-----------

系统定位为法律知识科普和辅助信息整理工具，不替代律师、仲裁机构或司法机关的专业判断。

系统必须：

* 明确区分用户事实、OCR 提取事实和 AI 推测内容。

* 不得伪造法律法规。

* 不得将证据识别结果直接视为真实证据。

* 不得承诺案件胜诉。

* 不得给出没有依据的确定性结论。

* 对信息不足的情况主动提示。

* 对法律法规适用时间和有效性保持谨慎。

* 在关键操作中保留用户确认环节。

第二十章 版本总结
=========

LexAgent V1.0 主要解决的是法律知识问答问题，通过 Multi-Agent 与 RAG 实现案件事实分析、法律法规检索、法律分析和可信度审核。

LexAgent V2.0 则进一步围绕真实法律援助业务进行扩展。

其核心不再只是让 AI 回答法律问题，而是让用户能够围绕一个具体案件持续开展信息整理、证据管理、法律咨询和处理建议获取。

**V1.0：解决法律问题的智能问答。**

**V2.0：围绕案件提供持续性的法律辅助服务。**

通过案件管理、证据智能分析、智能证据清单和法律问答质量评估等功能，使 LexAgent 从一个多 Agent 法律问答系统进一步发展为具有实际业务闭环的智能法律援助系统。
